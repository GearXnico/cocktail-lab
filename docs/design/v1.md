# cocktail-lab v1

Status: Draft · Author: GearXnico · Date: 2026-10-29 · Updated: 2026-11-14 (3D viewer, My bar, new families and recipe sources in v1)

## Problem

People learning mixology, bartenders, bars costing their menu and independent bartenders have no single
free place to look up reliable cocktail specs in Spanish and English and work out what each drink costs.
Today they combine recipe sites with spreadsheets, and costing a whole menu means copying bottle prices
and specs by hand, with no consistent rule for waste, target cost or tax.

## Goals

- A curated, bilingual (es/en) recipe library: 12 families (one of them alcohol-free), at least 5 recipes each and about 79 in all, with search and filters.
- A pour-cost calculator: cost per ml or unit, cost per drink with waste, suggested price from a
  target cost %, optional tax, in the user's currency.
- A menu builder: pick recipes, see cost, margin and price, print or export.
- My bar: the ingredients a user has priced are their bar; the app lists the recipes they can make and those missing one ingredient.
- An interactive 3D model of each drink, built in code from the recipe data, with a step-by-step mode that follows the recipe: serving glass, each ingredient into the preparation vessel in order, ice, technique, strain or pour into the glass, garnish.
- No login: each user's prices and menus stay in their browser, portable through a file.

## Non-goals

- Imported 3D models or photos of drinks: the viewer builds every drink from data ([ADR 0006](../adr/0006-procedural-3d-drink-viewer-in-v1.md)).
- Event quoting: later.
- Accounts, server-side storage, sync between devices.
- Deployment and hosting.
- User-submitted recipes (recipes change through pull requests only).

## Options

All three keep recipes as JSON in the repo and user data in localStorage. They differ in what serves recipes and costing.

| | A. Static SPA only (simplest) | B. Fastify API + SPA + shared core | C. Express API + SPA + shared core |
| --- | --- | --- | --- |
| Recipes list/search/detail API | No: data bundled into the web | Yes | Yes |
| Stateless costing API | No | Yes | Yes |
| Zod validation of requests | n/a | First-class via `fastify-type-provider-zod`; schemas type the handlers | Hand-written middleware; types kept in sync by hand |
| Typed routes in TS | n/a | Built in (route generics) | `@types/express`, partial |
| API tests in Vitest | n/a | `app.inject()`, no open port | `supertest` |
| Works offline / with API down | Fully | Costing and menus yes (local); recipe browsing no | Same as B |
| Effort | Lowest | Medium | Medium |
| Risk | Fails the agreed scope (no API) | Less familiar to some contributors than Express | More glue code to keep types and validation aligned |
| Cost | $0 | $0 | $0 |

## Recommendation

**B: an npm-workspaces monorepo with a shared `core` package (Zod schemas, costing, search), a Fastify API and a React SPA.**
Fastify takes Zod schemas as route schemas, so validation, TS types and errors come from one definition,
and `inject()` makes API tests fast. The costing function lives in `core` and runs in the browser, so
users' prices never leave their device; the API's costing endpoint calls the same function.
If the API ends up with no consumer other than our own web, A is cheaper and works offline;
if most contributors only know Express, C costs a little more glue but nothing structural.

## Design

**Layout**

```
packages/core   Zod schemas, unit conversion, costing, search (pure TS, no I/O)
apps/api        Fastify; loads data/ at startup, keeps it in memory
apps/web        React + Vite, react-i18next, localStorage store
data/           ingredients.json, recipes/<family>/<slug>.json
scripts/        validate-data.ts (run in CI)
```

Package manager: npm workspaces.

**Data (recipes, in the repo)**

- `L = { es: string; en: string }` for every user-visible text.
- `Ingredient`: `id`, `name: L`, `category` (spirit, liqueur, wine, syrup, juice, bitters, soda, fresh, other),
  `base?` (gin, rum, tequila, mezcal, pisco, whisky, vodka, cachaca, brandy, sparkling-wine, wine, beer, aperitif), `measure: 'ml' | 'unit' | 'g'`,
  `description?: L` (one or two sentences for the ingredient page), and two optional fields for the viewer:
  `color?` (`#rrggbb`, the colour it pours in), `form?` (`pour`, `drop` or `scoop`; when absent, `ml` pours and `unit` or `g` drops)
  and `unitMl?` (the volume of one unit of a liquid counted in units, such as an egg white).
- `Recipe`: `schemaVersion: 1`, `id` (slug), `family`, `base`, `name: L`,
  `ingredients: { ingredientId, amount, unit: 'ml' | 'dash' | 'barspoon' | 'unit' | 'g', topUp?: boolean }[]`,
  `technique` (shake, dry-shake, stir, build, throw, swizzle, blend), `glass` and `ice` (fixed lists in the schema), `garnish?: L` (omitted when the spec has none),
  `steps: { es: string[]; en: string[] }`, `difficulty: 1 | 2 | 3`, `history: L`, `sources?: string[]`,
  and optional fields used by the viewer, the illustrations and the filters:
  `color?` (the drink's colour, `#rrggbb`), `cloudy?: true` (opaque liquid), `foam?: true` (egg-white head),
  `garnishKinds?` (a fixed list: `lime-wheel`, `lime-wedge`, `lime-twist`, `lemon-twist`, `lemon-wheel`, `lemon-wedge`,
  `orange-twist`, `orange-wheel`, `orange-wedge`, `cherry`, `olive`, `mint`, `pineapple`, `salt-rim`, `bitters-drops`, `spice-dusting`)
  and `taste?` (`citrus`, `bitter`, `sweet`, `dry`, `fruity`, `herbal`, `spiced`). The free-text `garnish` stays as the text people read;
  `garnishKinds` draws the main garnish (for the Dry Martini, the lemon twist, not the olive offered on request).
  `iceAfter?` is the number of ingredient lines added before the serving ice, for drinks built over ice partway (Mojito, Caipirinha); when absent, the ice goes in first.
  Ingredients are listed in the order they go into the vessel, so the step mode can follow them; `validate-data` cannot check this, the maintainer does.
  These lists come from the 3D spike and only ever gain values. Layered drinks (the Terremoto's grenadine) are drawn as one liquid for now.
- Families `coffee-after-dinner`, `juleps-smashes`, `aperitivo`, `hot-drinks`, `beer` and `mocktails`; base `none` for alcohol-free recipes.
  Mocktails are well-known alcohol-free classics, and the maintainer approves each family's list before its recipes are written.
- New schema values for these families: technique `heat`; glasses `mug` (heat-proof), `julep-cup`, `pint` and `shot`.
  The 3D viewer draws each new glass with its own lathe profile, and `heat` with a pot as its vessel.
- Sources ([ADR 0007](../adr/0007-recipe-sources-iba-then-diffords-guide.md)): the IBA spec when one exists; otherwise, or when the IBA spec is outdated, Difford's Guide;
  for regional classics with neither (Chilean drinks), a published source the maintainer accepts. Every source's URL goes in `sources`.
  Only measures are taken from a source: steps and history are written for cocktail-lab, never copied, and recipes are looked up one at a time (no scraping).
  When sources disagree, the maintainer decides; the maintainer reviews every recipe PR.
- Citrus naming, so the same fruit is never split across two ingredients: `lime-juice` is "Jugo de lima" (the Persian lime);
  the Pica lemon ("limón de Pica") and the key lime ("limón sutil") share one separate ingredient, `key-lime-juice`;
  the common lemon is `lemon-juice` ("Jugo de limón"). An ingredient is added to the catalogue only when a recipe needs it.
- Unit conversion in `core`, one table: dash = 0.8 ml, barspoon = 5 ml. A barspoon is also valid for an ingredient measured in `g` (dry sugar); costing converts it at 4 g per barspoon. `topUp` amounts are a nominal ml value used for cost, taken from the spec when it gives an amount or says "splash"; only when it gives none is it estimated as the glass capacity (about 250 ml for a normal glass) minus the other ingredients and the space taken by the ice or ice cream. The web shows these lines as "Completar con <ingrediente> (aprox. N ml)" / "Top up with <ingredient> (approx. N ml)".
- `validate-data` checks each file against the Zod schema, that ids are unique, that every `ingredientId`
  exists, that units fit the ingredient's measure, that file name and folder match `id` and `family`, that both languages are non-empty
  and have the same number of steps. CI fails on any error.
  The minimum of 5 recipes per family is a warning in `npm run validate-data` and an error with `--release`, which CI runs only on pull requests into `main`,
  so family pull requests can land one recipe at a time and a release cannot ship incomplete.

**Data (user, in the browser)**

- One localStorage key `cocktail-lab:v1`:
  `{ version: 1, currency, locale, defaults: { wastePct, targetCostPct, taxPct?, taxIncluded: true, roundingStep, displayUnit: 'ml' | 'oz' }, prices: { [ingredientId]: { price, size, measure } }, menus: { id, name, items: { recipeId, priceOverride? }[] }[] }`.
- `displayUnit` defaults to `'oz'`. It only changes how amounts are shown: recipe data, costing and the API stay in ml. Only `ml` lines that are not `topUp` are converted; `dash`, `barspoon`, `unit`, `g` and top-up lines are shown in their own unit, so "0 oz" never appears.
- `roundingStep` defaults to 100 for CLP and to the currency's minor unit (no extra rounding) for other currencies.
- Export downloads `cocktail-lab-YYYY-MM-DD.json`; import parses it with the same Zod schema (≤ 1 MB),
  shows a summary and replaces current data after confirmation.
- `version` plus a chain of migration functions for future schema changes.

**Costing (`core`, pure functions)**

- `unitCost = price / size` (per ml, unit or g).
- `drinkCost = Σ(amount_in_measure × unitCost) × (1 + wastePct)`.
- `rawNet = drinkCost / targetCostPct`.
- Tax included (default): `menuPrice = ceil(rawNet × (1 + taxPct) / roundingStep) × roundingStep`, `netPrice = menuPrice / (1 + taxPct)`.
  Tax not included: `menuPrice = netPrice = ceil(rawNet / roundingStep) × roundingStep`, and tax is added on the bill.
  No tax set: `taxPct = 0`.
- `margin = netPrice − drinkCost`, `marginPct = margin / netPrice`, `costPct = drinkCost / netPrice`, all from the rounded price.
  With a `priceOverride`, the same formulas use the override as `menuPrice`.
- Compute in plain numbers, round once at output to the currency's fraction digits from `Intl.NumberFormat`.
- An ingredient without a price makes the drink cost "incomplete" (listed missing items), never zero.

**My bar (`core`, pure functions)**

- The bar is the set of ingredients with a price in the user's data; there is no second list to keep in sync.
- `missingFor(recipe, bar)` returns the recipe's ingredient ids not in the bar. Only `ingredients` count: the garnish is a separate field, so it is never missing.
- The My bar page lists recipes with nothing missing, then those missing exactly one, each with the missing ingredient named.

**Interfaces (API, `/api/v1`)**

- `GET /recipes?q&ingredient&base&technique&glass&difficulty&family&lang&page&limit` → `{ items: RecipeSummary[], total }`.
  Filters combine with AND; repeated values of one filter combine with OR. `limit` ≤ 50 (default 20), `page` starts at 1.
  `q` matches the recipe name in either language, ignoring case and accents; `lang` (`es` default, `en`) only chooses the language the list is sorted by.
  `ingredient` takes ingredient ids. `RecipeSummary` is `id, family, base, name, technique, glass, ice, difficulty, ingredientIds`.
- `GET /recipes/:id` → `Recipe`, or 404.
- `GET /ingredients` → `Ingredient[]` (used by the price editor).
- `POST /costing` → body `{ recipeId | ingredients[], prices[], wastePct, targetCostPct, taxPct?, taxIncluded?, roundingStep?, currency }`,
  response `{ lines[], drinkCost, netPrice, menuPrice, margin, marginPct, costPct, missing[] }`. No state, nothing logged from the body.
  Body ≤ 16 KB, `ingredients` ≤ 30 lines, `prices` ≤ 100, one price per ingredient; `currency` must be a real ISO 4217 code.
  `lines[].cost` is the cost of that line before waste, rounded to the currency's fraction digits, so the rounded lines can differ by a minor unit from the rounded `drinkCost`.
  A price in a different measure than the ingredient's counts as no price: the ingredient goes in `missing[]`, the totals are `null` (never 0) and its line has `cost: null`.
  Limits: `size` 0.001 to 1e9, `price` 0 to 1e9, `targetCostPct` 0.01 to 1; a result that is not finite answers 400.
  Unknown `recipeId` → 404; unknown ingredient or unit that does not fit → 400.
- `GET /health`.
- Errors: `400 { error, issues[] }` from Zod (each issue is `{ path, code, message }`), `404`, `500 { error }` without stack traces.

**Web**

- Pages: recipe list (search + filters in the URL query, an SVG illustration per card built from `glass` and `color`), recipe detail (with cost for the user's prices, the 3D viewer and its step mode), My bar, ingredient page (description and the recipes that use it),
  prices editor, menu builder, menu print view.
- UI strings in `locales/es.json` and `locales/en.json`; language from the browser, switchable, saved locally.
- Recipes come from the API (cached per session); costing calls `core` locally.
- A ml / oz selector (`displayUnit`) in the settings; recipe amounts are converted for display with the `core` function (`displayAmount`).
- Menu: print view with CSS `@media print` (customer view: name, garnish, price; internal view: cost, cost %, margin);
  export as CSV and JSON. PDF comes from the browser's print dialog.

**Failure modes**

- API down → recipe pages show a retry message; prices, menus and costing for already loaded recipes keep working.
- localStorage unavailable or full → app runs in memory, shows a banner, export still works.
- Stored data fails validation → copied to `cocktail-lab:v1:corrupt`, user offered a download, app starts empty.
- Bad recipe JSON → CI fails; the API also validates at startup and refuses to start.
- Imported file invalid → rejected with the field errors; current data untouched.

**Security and privacy**

- No accounts and no personal data on the server; prices and menus never leave the browser.
- All API input validated with Zod; body limit 64 KB; arrays capped (≤ 100 ingredients); CORS restricted to the configured web origin.
- Imported files parsed as JSON only, rendered as text by React (no `dangerouslySetInnerHTML`).
- CI: `npm audit --audit-level=high` and gitleaks on every PR. Rate limiting is left to the deployment design, and so is Fastify's `trustProxy`: both are defined when the deployment is decided, because the client IP they depend on is only known behind the chosen proxy. Until then the API has neither.

**Testing**

- `core`: table tests for unit conversion and costing (hand-computed fixtures in CLP, USD, EUR; tax included and not; rounding steps), search normalisation, schemas, `missingFor`.
- `web` 3D viewer: a test that every value of `glass`, `ice` and `garnishKinds` builds a model without errors (headless, no WebGL needed for the scene graph), that the steps follow the recipe's ingredient order, use the vessel the technique implies and skip the serving ice when `ice` is `none`, and that the WebGL fallback works.
- `api`: Vitest + `inject()` for every route, filters, pagination, 400/404.
- `web`: Vitest + Testing Library for the store (migrations, import/export), filters and menu calculations.
- Data: `validate-data` in CI.

**Observability**

Fastify's pino logs with request id, method, route, status and duration; no request bodies. No metrics (no deployment).

**Rollout and rollback**

No deployment. Each PR merges into `dev`; v1.0.0 is released from `dev` to `main` when the plan is complete.
Rollback is a revert on `dev`. The user-data `version` field protects future releases from old browser data.

## Decisions to record

- Monorepo with npm workspaces and a shared `core` package for schemas, costing and search.
- Fastify over Express for the API.
- User data in the browser only (localStorage + file export), no accounts.
- Recipes as versioned JSON in the repo, validated with Zod in CI; IBA specs when they exist.
- Recipe sources: IBA first, then Difford's Guide ([ADR 0007](../adr/0007-recipe-sources-iba-then-diffords-guide.md)).
- Costing runs in the browser; the API costing endpoint is a stateless mirror of the same function.
- A 3D drink viewer built in code with three.js, in v1 ([ADR 0006](../adr/0006-procedural-3d-drink-viewer-in-v1.md)).
